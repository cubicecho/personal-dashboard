# Architecture Overview

Personal Dashboard composes the cubicecho apps — **auto-cal**, **notes**, **philotes** — into one app while each stays an independently runnable microapp. Composition happens at two layers:

1. **Data:** federated GraphQL. Each app exposes a federation subgraph; a self-hosted gateway composes them into one supergraph the dashboard queries.
2. **UI:** each app keeps its own standalone UI, *and* publishes its reusable domain components (with colocated GraphQL fragments) as npm packages the dashboard mounts directly. The dashboard adds new unifying UI (widgets, cross-app views) on top.

## Decision summary

| Concern | Decision | Doc |
|---|---|---|
| GraphQL composition | Apollo-style Federation v2, **Hive Gateway** self-hosted, supergraph composed offline (no cloud accounts) | [federation.md](federation.md) |
| Making apps subgraphs | New package `@cubicecho/federation` with `toSubgraph(schema, opts)`; each app mounts the result at a **new `/subgraph` endpoint**, `/graphql` untouched | [federation.md](federation.md) |
| Identity / SSO | Small OIDC service on panva `oidc-provider` (magic-link login UI); apps verify via JWKS and **map users by email**, keeping their own users tables + native auth for standalone mode | [auth.md](auth.md) |
| UI reuse | npm-published `@cubicecho/{autocal,notes,philotes}-ui` packages shipping raw `.tsx` source + colocated fragments; one Apollo Client v4 in the dashboard against the gateway | [ui-sharing.md](ui-sharing.md) |
| MCP | One `/mcp` on the dashboard server via `@cubicecho/graphql-mcp` `createHttpExecutor(GATEWAY_URL)` | [federation.md](federation.md#mcp-at-the-gateway) |
| Deployment | Docker Compose on the home server, all services on real Postgres | [deployment.md](deployment.md) |
| auto-cal tasks/habits/projects extraction | Out of scope, but the architecture makes it a drop-in: a future service is just a 4th subgraph claiming those root fields + re-compose | [roadmap.md](roadmap.md) |

## Why this works well

All three apps already share one stack, so integration is composition rather than translation:

- npm-workspaces monorepos (`app|client`, `server`, `db`), Node 22 running TS natively via `--experimental-strip-types` (no build step)
- Express + Apollo Server 5; GraphQL is the entire API (plus small REST side-channels: iCal, avatars)
- Drizzle ORM, dual backend: Postgres via `DATABASE_URL`, else embedded PGlite
- Expo / React Native Web + expo-router + NativeWind, Apollo Client
- Schemas built **programmatically**: `@vantreeseba/drizzle-graphql` `buildSchema(db)` → hand-written SDL extensions + resolvers → a security wrapper
- Magic-link auth, semantic-release, Biome, GraphQL Codegen

Each app builds its final schema at a single seam — the exact place `toSubgraph()` wraps:

| App | Schema seam | Security wrapper |
|---|---|---|
| auto-cal | `auto-cal/server/src/schema/index.ts` | `blockUnscopedResolvers` (only `my*` + magic-link fields live) |
| notes | `notes/server/src/schema/index.ts` (`buildAppSchema`) | CASL via `@vantreeseba/graphql-casl` `applyPermissions` |
| philotes | `philotes/server/src/schema.ts` | row-level user scoping (`applyUserScopeExtensions`) |

## Repo layout (this repo)

```
personal-dashboard/
  package.json            # npm workspaces: app, server, auth, gateway
  codegen.ts  biome.json  docker-compose.yml  Dockerfile
  gateway/
    gateway.config.ts     # Hive Gateway config
    supergraph.graphql    # checked in, generated by compose script
    api-schema.graphql    # checked in, public schema for client codegen
    scripts/compose.ts    # fetch {_service{sdl}} from subgraphs → compose → write both files
  auth/                   # OIDC service: oidc-provider + magic-link interaction + drizzle store
    src/index.ts  src/interactions.ts  src/adapter.ts  Dockerfile
  server/
    src/index.ts          # Express: static app/dist + SPA catch-all, /mcp, proxy /graphql → gateway (ws:true)
    src/mcp.ts
  app/                    # Expo shell: expo-router, Apollo v4 → same-origin /graphql, OIDC PKCE login, widgets
    metro.config.js  tailwind.config.ts  babel.config.js  src/  app/
  packages/               # (optional) dashboard-only shared UI
```

The dashboard container proxies `/graphql` (HTTP + WS upgrade) to the gateway so the client keeps the org's relative-URL, same-origin convention — no CORS, no `EXPO_PUBLIC_API_URL` in prod.
